# MLX端到端、事件延迟累加与真实GPU性能对照

2026-09-09用户澄清：串行事件流是延迟累加估计，外部主比较是端到端模拟与GPU实测；进一步考虑GPGPU模拟器或相同GPU架构模型。优先完整端到端、主要正确性和性能试验，合理框架数值差异不要求逐位消除。此协议取代先前将“实际串行周期执行”当作用户所指事件估计的解释，历史运行证据不改写。

## 四类数值必须分别标注

| 对象 | 数值来源 | 用途与限制 |
| --- | --- | --- |
| MLX串行事件估计 | 完整工作负载事件清单及预先登记的延迟模型，`C_event = sum(L(e))` | 快速估计；不计算完整模型数值，不形成真实的动态竞争/重叠；必须保留事件粒度、次数、延迟来源和被忽略项 |
| MLX端到端模拟 | 同一完整模型由C/C++后端实际执行的全局周期`C_e2e` | 验证真实数据依赖、调度、资源竞争和最终输出；内部比较`C_event / C_e2e`及逐项开销差异 |
| 真实GPU | 同一模型、权重、输入、精度、任务语义的实际测量时间`T_gpu` | 外部主基线；分别记录设备时间和含主机开销的端到端wall time |
| 同架构GPU模拟 | GPGPU-Sim/Accel-Sim实际执行/trace replay的周期及独立配置频率 | 先与对应实卡校准，再作为辅助架构比较；代理配置不能冒充匹配实卡 |

已有完整原生串行执行可提供事件延迟的测量来源和辅助数值交叉核对，但不是延迟累加估计器本身。不能从并发运行的`publish-start`（其中含驻留等待）求和，反过来宣称这是独立的无竞争服务延迟；也不能将FU时间和已包含FU时间的算子窗口重复累加。

事件估计必须消费完整图的全部事件实例和实际shape，输出覆盖计数与遗漏项；不允许缩小模型后按层数/FLOPs外推。已有微程序端到端正确性用于保证工作身份，估计结果本身不能作为数值正确性证据。

## 频率和计时范围

单一MLX参考时钟下，`T_mlx = C_e2e / f_mlx`，外部时间比为`T_gpu / T_mlx`；大于1才表示该口径下MLX更快。`configs/hardware/mlx_full.yaml`当前设置1.0GHz，可用作**项目设计假设**，不是硅片实测或已完成时序收敛的Fmax。具体报告要绑定该频率来源和所执行硬件参数，不把历史配置中的其他经验系数带入当前周期模型。

如果CPU、设备、互连、DRAM属于不同时钟域，应使用已经换算到共同参考时钟的真实全局时间，或分别按域处理；不能将不同域的周期直接相加。频率扫描若改变了核心/内存时间比，必须相应重跑模型或明确标为固定周期结果的换算敏感性，不能假设所有瓶颈都按核心频率线性加速。

GPU以直接测得的毫秒为主，不需要用一个名义GPU频率倒算wall time。记录实际SM/显存频率样本、驱动、功耗上限、温度/节流、是否锁频、是否有其他负载。默认不改变整卡时钟/功耗设置。存在DVFS时，不能用峰值频率将时间强行归一化为“等频性能”。

MLX与RTX4090是不同架构，二者时间差是架构/实现性能差异，不叫“MLX模拟误差”；只有同一GPU架构的模拟与对应实卡在匹配条件下的偏差，才用于评估GPU时序模型的准确性。不能仅凭MLX与GPU速度接近来证明MLX模拟器正确。

GPU计时至少包括：预热后的重复测量、计时前后同步、CUDA event设备区间，以及独立的同步wall time。报告中位数、分位数和波动范围；CUPTI/Nsight kernel总和是辅助项，不等于跨stream或CPU launch存在时的端到端延迟。跟踪/插桩运行与正式性能测量分开，避免将trace采集开销算入GPU基线。

公平比较须对齐：完整checkpoint与参数规模；batch、prefill长度、decode步数、KV语义、padding；dtype/累加策略和合理结果误差；attention实现、TF32等库选项；权重/输入是否驻留；是否包含H2D/D2H、主机launch、同步及后处理。原生MLX尚未包含真实CPU/冷装载时，只可比较明确匹配的设备侧范围，不能称为完整系统TTFT。Rocket完整运行后再补真正系统口径。

已完成的旧串行Llama2设备周期为434,772,345,599；在明确假设1GHz时等于434.772345599秒，**不是当前配对端到端的性能结论**。这一实现可能慢于GPU，结果应如实报告并定位搬运、复用和调度缺口，不通过改频率或选择统计口径制造加速。

## 当前GPU及开源模拟器条件

本机只读查询确认两张NVIDIA GeForce RTX4090，各24GiB级显存。空闲采样中的频率不是推理期间频率；正式运行需要持续记录。现有Llama2 GPU数值参考为`cuda:1`，但数值参考采集日志不提供可直接冒充正式性能结果的时间。

仓库已有[RTX3090 proxy](gpgpusim-rtx3090-proxy.md)，从SM86 RTX3070测试配置修改SM数量、内存分区和频率；既有结果是vector/BSMM/FFT/SWA代理kernel，不是本轮完整Llama2/BERT，也不是SM89 RTX4090同架构校准。不能直接用旧代理数值充当GPU完整端到端性能。

上游[Accel-Sim](https://accel-sim.github.io/)提供NVBit SASS采集、GPGPU-Sim性能回放、实卡相关性工具和参数tuner；当前2.0还列出H100/H200支持。2026-09-09查阅的[标准配置表](https://github.com/accel-sim/accel-sim-framework/blob/d930ad6d02c09bb56867132583735aba0389cff4/util/job_launching/configs/define-standard-cfgs.yml)包含RTX3070、A100、H100/H200等，但未列RTX4090/SM89。这只说明该标准表没有匹配项，不据此断言任何第三方都不支持4090。

优先评估SASS trace驱动路线，以尽量保留实测中真实CUDA库/kernel选择；[GPGPU-Sim说明](https://github.com/gpgpu-sim/gpgpu-sim_distribution/blob/dev/README.md)也区分执行驱动与Accel-Sim的SASS trace支持。trace回放是性能模型，不自动证明重新计算了模型logits。旧NVBit1.7.3在本机驱动上曾失败，新版兼容性必须重新实测，不能沿用“旧版失败＝所有版本失败”的结论。

GPU模拟补充实验的进入条件：固定工具commit、检查指令/库/驱动兼容；明确GPU架构、SM数、Tensor Core、cache、内存、各时钟域；用同实卡微基准独立校准；再覆盖本轮完整模型的实际kernel/事件，而不是只取一层trace外推。若只能使用Ampere等代理配置，就标注代理和校准缺口，不称4090预测，也不让该扩展阻塞先完成GPU实测对照。
