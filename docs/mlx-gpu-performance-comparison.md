# MLX端到端／事件驱动误差与GPU模拟／实机误差

执行优先级更新：按用户最新要求，先完成MLX与Chipyard整模主线验收（主要正确性、并发端到端、完整事件驱动及模型间误差），GPU实机/模拟器新增实验暂缓；GPU工作优先于最后的RTL/PPA。本文保留GPU实验规范及已有结果，不表示当前继续扩展GPU支线。

2026-09-09用户最终澄清：**MLX比较端到端执行模拟器与事件驱动模拟器的性能差异，两者都要考虑并发/调度；GPU比较GPU模拟器与RTX4090实机测量的误差。** 事件驱动不是“串行执行”或“不考虑并发的延迟累加”的同义词。以下口径取代之前的串行／并发消融解释，历史运行证据保留但不重标为所需主实验。

| 误差对象 | 参照值 | 待比较值 | 有符号相对误差 |
| --- | --- | --- | --- |
| MLX | 同配置的完整端到端执行模拟`C_e2e` | 考虑并发/调度的事件驱动模拟`C_event` | `(C_event - C_e2e) / C_e2e` |
| GPU | RTX4090实测`T_real` | 匹配RTX4090配置的GPU模拟`T_sim` | `(T_sim - T_real) / T_real` |

同时报告绝对差和绝对相对误差。MLX没有实芯片测量参照，不称为“MLX对实机误差”；GPU误差不以另一个GPU调度模型或串行估计为分母。MLX与GPU之间的速度比可以另外报告，但不属于上述任一误差。

## 架构与消融的共同原则：保留并发

用户进一步明确：GPU与空间加速器的正式架构比较和消融都应支持并发，研究的是并发利用率、调度效率的差异，而不是将某一方改成串行再比较。GPU模型保留SM间block并行、SM内warp驻留/发射及访存隐藏；MLX模型保留多PE、受限上下文驻留、事件唤醒和不同流水线的并行。二者的并发语义与资源单位不同，不能以相同线程数或任意扩容来强行对齐。

MLX事件驱动与端到端模型使用相同并发能力与资源约束；事件驱动仅改变时间推进/建模抽象，不意味着关闭并发。GPU模拟按对应实卡能力建模，再与实测比较。

消融每次只改变一个具体机制，例如准入策略、就绪候选排序、跨层事件流水或模板装载策略；其余并发能力保持不变。关闭跨层流水时仍保留层内PE与上下文并发，不能退化为整个机器一次只执行一个工作单元。报告合法驻留数、就绪/发射利用率、依赖与资源等待、有效重叠、访存隐藏和最终完成时间。

现有逐算子串行路径仍可能包含算子内部的多PE/多上下文并发，不能将“算子顺序提交”与“硬件完全无并发”混为一谈。但它不足以充当目标MLX多层并发架构的正式性能基线，相关结果只保留为历史调试证据，不替代上述两个保留并发的主实验。

## 分析内因：并发效率与有效资源利用

用户明确：延迟/吞吐是性能的外显结果，并发效率与资源使用效率是主要内因。报告以“架构资源和执行策略 → 数据供给/就绪状态 → 准入与发射 → 有效并发/资源利用 → 完成时间”为分析主线，不只列周期或速度比。

| 内部指标 | 必须区分的量 | 可定位的机制 |
| --- | --- | --- |
| 上下文并发 | 已驻留、就绪、实际在途、实际发射的block/warp/tag数 | 槽位限制、事件/数据等待、调度选择、饥饿 |
| 发射效率 | 就绪且可发射机会、实际发射、端口/FU/回压阻塞 | 仲裁、共享端口、取指/操作数供给、流水线II |
| 计算利用 | 忙碌PE/FU周期、有效lane工作量、可用容量 | 尾部掩码、负载不均、依赖空洞、无效/重复工作 |
| 存储利用 | RF/SPM驻留峰值、端口服务率、有效与总搬运字节 | 容量占用不等于带宽利用；重复加载与低数据复用会增加流量 |
| 重叠/延迟隐藏 | 计算与搬运重叠、跨上下文/跨PE重叠、关键路径上实际隐藏的等待 | 高驻留数不保证隐藏延迟；非关键路径重叠不一定缩短任务完成时间 |

同一指标必须使用一致单位和分母，例如PE-cycle不能直接与全局cycle相除当成百分比，需结合实际PE数/可用容量；并发窗口的时长和计数不能重复加总。GPU的SM/warp指标与MLX的PE/context指标分别按本架构定义，不能把“相同占用率”直接当作相同执行效率。

已有C++周期后端有部分busy、compute/DMA overlap、同PE上下文重叠、准入停顿和写回停顿计数。它们只是可用证据，不代表上述指标全部已实现或已足够说明根因。缺少的“就绪但未发射”“有效lane/搬运复用”“关键路径等待”等项需补事件与计数，不能凭总延迟反推。

MLX模型间误差先按这些内部计数/时间线定位，再用同工作量、同资源和其他并发能力不变的单机制消融验证；GPU模拟对实机误差也应联合周期、发射/占用和cache/DRAM统计检查。相关性不是充分因果证据，资源忙碌率高也不自动等于高有效吞吐。

## 四类数值必须分别标注

| 对象 | 数值来源 | 用途与限制 |
| --- | --- | --- |
| MLX事件驱动模拟 | 完整工作负载的事件、依赖、延迟与资源模型，动态推进就绪事件并得到makespan `C_event` | 必须考虑并发、调度、重叠、有限资源和访存等待；不应简单求所有事件延迟之和，也不能不加约束地相减重叠 |
| MLX端到端模拟 | 同一完整模型由C/C++后端实际数据执行的全局周期`C_e2e` | 核对真实数据依赖、调度、资源竞争和最终输出；作为MLX事件驱动模型性能误差的参照 |
| 真实GPU | 同一模型、权重、输入、精度、任务语义的实测时间`T_real` | GPU模拟误差的实机参照；分别记录设备范围和含主机开销的端到端wall time |
| 同架构GPU模拟 | GPGPU-Sim/Accel-Sim实际执行/trace replay的周期及独立配置频率`T_sim` | 同样可以包含并发/调度；比较它与RTX4090实测的偏差，代理配置不能冒充匹配实卡 |

已有完整原生串行执行仅是辅助路径，不是用户要求的事件驱动模型。两套MLX模拟器必须对齐相同PE/RF/SPM/FU资源、映射、上下文与事件策略、访存参数和完整工作量；差异分析针对抽象粒度、延迟/等待模型、依赖可见性及实际数据执行开销，不默认把差异解释为“有没有并发”。不能把端到端运行的`publish-start`区间直接累加后当成独立预测，也不能重复计入FU与包含FU时间的算子窗口。

事件驱动模型必须消费完整图的全部事件实例和实际shape，输出覆盖计数与遗漏项，实际模拟并发完成时间；不允许缩小模型后按层数/FLOPs外推。已有微程序端到端正确性用于保证工作身份，事件驱动的性能结果本身不能替代端到端数值正确性证据。

## 频率和计时范围

单一MLX参考时钟下，`T_mlx = C_e2e / f_mlx`，外部时间比为`T_gpu / T_mlx`；大于1才表示该口径下MLX更快。`configs/hardware/mlx_full.yaml`当前设置1.0GHz，可用作**项目设计假设**，不是硅片实测或已完成时序收敛的Fmax。具体报告要绑定该频率来源和所执行硬件参数，不把历史配置中的其他经验系数带入当前周期模型。

如果CPU、设备、互连、DRAM属于不同时钟域，应使用已经换算到共同参考时钟的真实全局时间，或分别按域处理；不能将不同域的周期直接相加。频率扫描若改变了核心/内存时间比，必须相应重跑模型或明确标为固定周期结果的换算敏感性，不能假设所有瓶颈都按核心频率线性加速。

GPU以直接测得的毫秒为主，不需要用一个名义GPU频率倒算wall time。记录实际SM/显存频率样本、驱动、功耗上限、温度/节流、是否锁频、是否有其他负载。默认不改变整卡时钟/功耗设置。存在DVFS时，不能用峰值频率将时间强行归一化为“等频性能”。

MLX与RTX4090是不同架构，二者时间差是架构/实现性能差异，不叫“MLX模拟误差”；只有同一GPU架构的模拟与对应实卡在匹配条件下的偏差，才用于评估GPU时序模型的准确性。不能仅凭MLX与GPU速度接近来证明MLX模拟器正确。

GPU计时至少包括：预热后的重复测量、计时前后同步、CUDA event设备区间，以及独立的同步wall time。报告中位数、分位数和波动范围；CUPTI/Nsight kernel总和是辅助项，不等于跨stream或CPU launch存在时的端到端延迟。跟踪/插桩运行与正式性能测量分开，避免将trace采集开销算入GPU基线。

公平比较须对齐：完整checkpoint与参数规模；batch、prefill长度、decode步数、KV语义、padding；dtype/累加策略和合理结果误差；attention实现、TF32等库选项；权重/输入是否驻留；是否包含H2D/D2H、主机launch、同步及后处理。原生MLX尚未包含真实CPU/冷装载时，只可比较明确匹配的设备侧范围，不能称为完整系统TTFT。Rocket完整运行后再补真正系统口径。

已完成的旧串行Llama2设备周期为434,772,345,599；在明确假设1GHz时等于434.772345599秒，**不是当前配对端到端的性能结论**。这一实现可能慢于GPU，结果应如实报告并定位搬运、复用和调度缺口，不通过改频率或选择统计口径制造加速。

## 当前GPU及开源模拟器条件

本机只读查询确认两张NVIDIA GeForce RTX4090，各24GiB级显存。空闲采样中的频率不是推理期间频率；正式运行需要持续记录。现有Llama2 GPU数值参考为`cuda:1`，但数值参考采集日志不提供可直接冒充正式性能结果的时间。

仓库已有[RTX3090 proxy](gpgpusim-rtx3090-proxy.md)，从SM86 RTX3070测试配置修改SM数量、内存分区和频率；既有结果是vector/BSMM/FFT/SWA代理kernel，不是本轮完整Llama2/BERT，也不是SM89 RTX4090同架构校准。不能直接用旧代理数值充当GPU完整端到端性能。

上游[Accel-Sim](https://accel-sim.github.io/)提供NVBit SASS采集、GPGPU-Sim性能回放、实卡相关性工具和参数tuner；当前2.0还列出H100/H200支持。2026-09-09查阅的[标准配置表](https://github.com/accel-sim/accel-sim-framework/blob/d930ad6d02c09bb56867132583735aba0389cff4/util/job_launching/configs/define-standard-cfgs.yml)包含RTX3070、A100、H100/H200等，但未列RTX4090/SM89。这只说明该标准表没有匹配项，不据此断言任何第三方都不支持4090。

后续深入GitHub检索已找到RTX4090实际适配与校准记录，不能再停留在“标准表没有4090”的结论：见[RTX4090模拟器检索](rtx4090-simulator-search.md)。其中社区报告有193个kernel的周期相关性结果，同时保留缓存/DRAM计数的大误差；这是可试验候选，不是本项目已验收的4090模型。

优先评估SASS trace驱动路线，以尽量保留实测中真实CUDA库/kernel选择；[GPGPU-Sim说明](https://github.com/gpgpu-sim/gpgpu-sim_distribution/blob/dev/README.md)也区分执行驱动与Accel-Sim的SASS trace支持。trace回放是性能模型，不自动证明重新计算了模型logits。旧NVBit1.7.3在本机驱动上曾失败，新版兼容性必须重新实测，不能沿用“旧版失败＝所有版本失败”的结论。

GPU模拟补充实验的进入条件：固定工具commit、检查指令/库/驱动兼容；明确GPU架构、SM数、Tensor Core、cache、内存、各时钟域；用同实卡微基准独立校准；再覆盖本轮完整模型的实际kernel/事件，而不是只取一层trace外推。若只能使用Ampere等代理配置，就标注代理和校准缺口，不称4090预测，也不让该扩展阻塞先完成GPU实测对照。
