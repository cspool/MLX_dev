# 通用图的双算子 CPU 任务路由

本增量在已验收的[双算子设备 ABI](mlx-pair-system-abi.md)上连接完整图编译器和 C/RV64 主机任务表。周期推进、块准入、上下文发射、资源竞争及数值执行仍在 C/C++；Python 负责图编译、地址规划和证据审计。本次不修改加速器 RTL。

## 分组与存储

`compile_graph(..., block_pairs=True)` 从原始节点重新推导已登记的闭合算子对，保留每个源节点、原始源 ID、数值程序和全部矩阵 batch。它不要求两个节点相邻：生产者仅由该消费者使用时，将生产者延后到消费者的位置，与消费者组成一个设备任务；期间的其他节点仍执行。每个组启动前，外部输入的生产者必须已经完成。

串行生命周期不能直接用于这种调度。例如 `A → P`、独立算子 `B`、消费者 `C(P, B)` 的原串行布局可能在 P 结束后把 A 的地址复用给 B；若将 P 延后，P 就会读到 B。新编译器先校验原生命周期与完整 SSA 图，再按实际执行组重新规划所有存储根的闭区间。组内输入和两个输出必须同时存在；最后一个使用组结束后才可复用地址，64 字节对齐。资产保持只读并保留至图结束，最终输出也保留至 CPU 检查结束；合法视图继续共享其根分配。

这不是通过删除算子或调用其他数值后端消除冲突。未选入双算子组的节点继续使用原矩阵、向量、搬运、主机控制或已检查的视图路径。

## 版本化任务表

旧版 v1 的结构大小、保留字段规则与顺序执行路径保留。新 v2 沿用 128 字节 program、64 字节 task 和 64 字节 result，但显式赋予以下字段新含义：

| v2 字段 | 含义与检查 |
| --- | --- |
| `program.reserved[0]` | 指向 `source_count` 个 32 字节 `mlx_graph_source` 记录；其余 program 保留字仍必须为零 |
| source 记录 | 原始源 ID、依赖 ordinal 数组地址、依赖数、零保留字；依赖必须按 ordinal 严格递增且早于当前源 |
| `task.kind = 3` | 双算子设备任务，固定 8832 字节描述符；任务的 batch index/count 必须为 0/1，全部矩阵 batch 在设备内部执行 |
| 双算子 `task.reserved` | 消费者 ordinal + 1；必须是未完成的后继源，并与描述符中的消费者 ID 匹配 |

CPU 对每个源核对源表身份，拒绝重复执行及依赖未完成的任务。双算子消费者只有组内生产者这一依赖可以尚未完成；其他依赖仍逐一检查。设备成功且输出写入完成后，CPU 才同时写两个源的完成记录。失败不会产生两个虚假的完成标记。所有节点仍按原 ordinal 在最终 CPU 检查器中逐项核对。

v2 可以按依赖执行非连续源 ordinal，但一个未合并矩阵源的各 batch 仍必须连续并全部完成。旧 Spike MMIO 设备没有双算子能力，C runtime 明确拒绝向该设备提交 kind 3，不以旧串行数值实现冒充支持。实际双算子任务通过 Rocket/RoCC 系统入口执行。

## 已结束的组件检查

[pair-graph-003](../artifacts/tagged/pair-graph-003/report.json) 已通过 217 项回归、23 个 ASan/UBSan/LSan 重放，以及 26 项实际 RV64 任务表契约检查。覆盖实际串行地址复用冲突、非相邻生产者延后、双算子数值执行、8-batch 矩阵、正常/扰动三步生成的旧路径兼容性、依赖/身份/重复完成/版本错误及篡改证据拒绝。安全重放分别使用设备级和 RoCC 适配器级驱动，并保持观察开关不影响目标执行。这里的 RV64 契约检查不是新版双算子整图的 Rocket 验收。

完整公开 Llama2 程序的新编译保留 6181 个源节点，覆盖 873 个候选算子对（其中 192 对不相邻），形成 8284 个 CPU 任务，描述符共 31808512 字节。任务减少包含把同一矩阵源的多个 batch 封装到一个双算子设备描述符，不表示算量减少。新物理布局需要 13482060672 字节映射空间。

[独立存储区间检查](../artifacts/tagged/pair-graph-001/independent-storage-audit.json) 对 4802 个存储根及 14960 次源输入/输出访问做闭区间检查，未发现同时活跃分配的地址重叠；所有资产和最终输出均保持规定的生命周期。这些只是完整程序的编译与地址证据，**尚未执行该新路径的完整模型推理**。

## 系统验收状态与使用

`scripts/run_mlx_clocked_chipyard.py` 新增 `--block-pairs` 和 `--event-slots`，也允许 cases 条目的 `block_pairs` 布尔选择。launch map 同时记录两个源身份；系统结果审计检查实际生产者的全部 batch、双方数值工作量、资源与模板回收、事件 epoch 及物理响应守恒。完整模型审计的 ELF 重建会复用相同的 v2 编译参数。

最新 [pair-graph-rocket-003](../artifacts/tagged/pair-graph-rocket-003/report.json) 的四个完整登记图均已正常退出并通过 CPU 源完成/输出检查：非相邻算子图、8-batch 广播矩阵图、正常及权重扰动三步生成图。合计执行 99 个源调用、40 个设备窗口，其中 8 次双算子启动。正常生成序列为 1/2/2，扰动后为 0/0/0；下一轮 embedding 从实际 argmax 的结果取索引，cache 从上一轮输出增长到长度 1/2/3，不以参考值回填中间状态。

[镜像重建审计 004](../artifacts/tagged/pair-graph-image-audit-004/report.json) 使用 `scripts/audit_mlx_pair_graph_system.py` 重新生成四个完整 CPU ELF、描述符、输入载荷与检查器，均与实际执行版本逐字节相同，并逐窗口核对双方源身份、矩阵全部 batch、数值工作量、上下文预算、事件、模板及总线排空。审计器另有 [43 项检查](../artifacts/tagged/pair-graph-image-audit-tests-003/regression.xml)，包括篡改真实结果、未终态/重复 CPU 标记、参考 token 回填和 cache 重置的拒绝。该审计没有导出新的目标输出文件，也未校准内存时序，不能据此发布完整模型或推理性能结论。

失败历史保持可追溯：系统 001 在模型构造时因观察器不接受新增消费者字段退出 -6，尚未启动设备任务；之后补充了有界消费者元数据校验。组件 002 暴露了安全重放脚本混用设备级/RoCC级驱动的问题；现按报告类型选择驱动，观察日志重放到独立路径，不覆盖原始证据。系统 002 在输入清单尚未生成时准备失败，未启动模拟器。组件 003 与系统 003 是修正后独立的新尝试，没有改写这些失败记录。

一般 CDC、多消费者/不同形状映射、RF/NoC 直传、新路径完整模型端到端、全部目标模型、GPU 数值门槛、系统推理性能与 RTL 仍未完成。主工作树中的两项旧完整模型运行继续使用冻结版本，不能重标为采用了本增量。
