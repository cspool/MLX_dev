# MLX 指令集与空间并行调度的联合设计契约

本页依据当前代码接口和用户指定的“专题回答”组织设计。它不是作者原始 ISA，也不新增已编码或已实现的硬件功能。资料来源与边界见[卡片参考](mlx-dfu-simulator-reference.md)；实施顺序仍为 C/C++ 模拟器验证、系统集成、最后 RTL/PPA，Chipyard 整模验收仍优先。

## 先区分当前执行 profile

[早期 tagged ISA](mlx-native-isa.md)描述 `tagged_program.py`／`simulator_ext/tagged` 的子集。当前完整模型使用 `model_matrix_program.py`、`model_vector_program.py`、`model_memory_program.py`、`model_control_program.py` 及对应 C++ 后端。两者不能只因操作名相同而互换。

尤其不能把早期逐步 FP16 舍入的 MAC、其上下文设置或受限 lane 保持规则，自动应用到当前 F32 K-ascending 矩阵微程序。当前比较使用的阵列容量为每 PE 至多 2 上下文、16 个 RF 向量、32 个 ROM word，全阵列 128 个 SPM 向量；这是受检模型配置，不作为论文所有设计点的统一 ISA 常量。实际参数仍须由目标 profile 与编译产物核对。

## 联合设计的分工

| 层次 | 应表达的契约 | 不应混入的内容 |
| --- | --- | --- |
| 源图／空间映射 | 源和 batch 身份、独立任务、生产消费关系、输出区域、PE 映射 | 不能把所有任务都当可独立执行，也不能把源 ID 或宿主对象槽当 PE／LCM 编号 |
| PE 指令／微程序 | 操作数、dtype、lane/mask、状态读写、转换与累加、访存及完成可见性 | 不能仅凭同名 ADD/MAC 判断数值语义相同；不虚构未验证的通用分支或通信模式 |
| 控制／搬运接口 | 描述符字段、实际地址、请求身份、错误、完成条件、guard | RV64 ALU 叶程序不等于完整 Rocket CPU；文件装入不等于目标 DMA |
| 驻留／发射调度 | 有限资源准入、输入就绪、单元／端口竞争、完成发布及回收 | Task 不固定绑定某个 FU；具体 latency、II、仲裁策略通常属于微架构 profile，不必变成 opcode |
| 宿主模拟器表示 | 模式文件缓存、紧凑运行段、对象／事件／ROM 记录复用 | 这些不是新的 MLX 指令，也不增加硬件 RF、SPM、ROM 或事件槽 |

LCM 与其他论文层级的准确职责，应以论文和对应实现逐项对照后命名；当前 Source、Block、PE、Context 不能未经验证直接重命名为 LCM、SM 或 warp。可以借鉴 GPU 两级调度的职责划分，不自动引入独立线程 PC、分支重汇合或任意线程块语义。

## 空间任务的状态契约

以下是逻辑状态转换，不是新增二进制指令名：

1. **提交源。** 验证编译后端、父依赖、全部窗口和输出区域。源进入活动集合即占前端槽，即使尚未取得 PE。
2. **准入块实例。** 逻辑身份由源、batch、块序号组成；按映射查询 PE／上下文及 RF/SPM/ROM 需求。容量不足保持等待，不能自动扩容或提前占用不存在的硬件线程。
3. **选择就绪工作。** 分开检查输入可见、模板可用、功能单元和共享端口。不同任务可在不同单元重叠，但同一资源仍受带宽与驻留约束。
4. **完成与发布。** 功能结果、写响应、块数据范围和后继可见边沿分别明确。发出 store 不等于结果已可消费；全部 batch 未结束不能发布整个源完成。
5. **回收。** 实际消费者结束前保持必要数据存储。硬件 lease、事件 epoch 与宿主对象槽分离；复用宿主槽不得改变逻辑顺序或让旧完成事件命中新实例。

当前事件源图只接入 whole-source 父依赖。既有原生 `BlockFlow`／`CompletionWindow` 还提供块准入、输入就绪、完成通知、epoch、lease 和有限事件记录；独立事件模型必须接入对应协议，不能将配对程序静默降为整源屏障。

## 指令、实例和地址必须共同验证

每种新增或修订执行模式应记录下列项目，再决定需要 PE opcode、控制描述符还是编译期展开；不能先分配操作码再补理由。

- 硬件支持与来源类别：现有实现、论文明确语义、待检验推测或项目编码选择。
- 输入输出与状态：dtype、有效 lane、舍入／溢出规则、累加初值、未覆盖区域以及跨阶段保留范围。
- 空间和时间映射：输出 tile、PE、阶段、实例次数、尾部规则及依赖数据范围。
- 地址契约：原始 root/shape/stride/offset、batch 广播、有效字节与触及范围；不得假定逻辑二维窗口已经连续化。
- 资源与完成契约：RF/SPM/ROM／事件槽需求、服务 latency/II 所属 profile、反压、结果可见边沿、失败和排空。
- 编译与执行路由：生成器、描述符／机器字、C++ 解码与执行入口、系统装载及结果检查。

GEMM 的独立输出 tile 可以空间并行；同一输出 tile 的 K 累加则必须保留依赖与状态。模板／实例复用只能减少宿主描述冗余，不能减少 K 次数、初始化、尾部或回写。规约与广播也必须保留实际依赖；从 COPY 接口不能推断未给出的 NoC 路由、带宽或一般 barrier。

## 对下一步实现的直接要求

紧凑块运行段应承载“重复数量＋映射规律＋模式引用＋地址／实例绑定”，而不是作为新 ISA。C++ 只生成当前活动源窗口的下一个待准入块，采用稳定逻辑序号调度，退休后回收宿主描述；有界 trace 限制日志，不限制执行工作量。

正式合并条件不是仅通过解析：紧凑／预展开版本必须匹配全部动态实例、源／块完成边沿、请求／响应、数值结果和硬件资源计数；流式块协议要覆盖槽耗尽、反压、错误 epoch、重复完成和存储过早回收。最终再用完整模型两条并发路径核对性能误差与内部利用率。

此页只是设计契约的落地，不表示紧凑块生成器、完整流式事件图、完整论文 ISA 或 Chipyard 整模已经通过。
